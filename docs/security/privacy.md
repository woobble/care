# Client data and privacy

Client addresses, contact details, insurance identifiers, representation references, Pflegegrad records, and notes are personal data. They remain in the tenant-owned client module and are protected by API authorization, scoped parent-client access, application tenant predicates, and forced PostgreSQL RLS.

The application does not log client request bodies or child-resource values. Audit metadata records resource IDs and changed-field names rather than copies of personal values. Versioned outbox payloads use resource IDs and operation metadata. Client timeline responses are a client-oriented projection and omit raw audit metadata. Validation errors are generic and do not echo submitted values. Insurance identifiers are only rendered in the authorized client detail workflow and are never included in list search or timeline output.

All users with an applicable `client.read` grant can read the client child resources through the API; this slice does not define separate permissions for insurance identifiers or contact details. Review this access boundary before adding broader caregiver workflows. Contact notes are length-limited and the UI explicitly discourages medical information there.

Service catalog data is operational configuration. It is tenant-isolated and has separate `service.read` and catalog mutation permissions. It contains no prices, claims, or billing records.

Scheduling reveals that a client has a planned visit, along with only the display name, provider, time, planned service snapshots, status, and assigned employee names needed for coordination. Calendar responses omit insurance, Pflegegrad, contacts, and full client history. Visit notes are not copied into audit metadata or outbox events. Caregiver execution views contain only operational visit data and require an active employee link and assignment. Execution details follow visit/client scope for Office readers. Operational notes and service notes are not copied into audit metadata or outbox events; the client timeline contains only high-level started/completed summaries. A planned visit is not a care record or evidence of service delivery.

Care documentation entries, service-evidence notes, and amendments contain sensitive narrative care data. They are available only through authorized visit/documentation detail reads; the Office worklist returns metadata and structured missing-requirement codes without note snippets. There is no full-text search. Audit metadata, documentation history metadata, and outbox payloads contain identifiers and change metadata but never narrative text. The client timeline shows fixed summaries only for incident recording, finalization, and amendment. Finalized content remains immutable; corrections append a separately attributed amendment.

Service-evidence packages contain only the service facts shown to a signatory and are immutable snapshots. Acknowledgement history snapshots the signatory's name and capacity. Decline notes are protected detail data and are omitted from audit, logs, and outbox events. Signature strokes are sensitive personal data stored in a private S3-compatible bucket; PostgreSQL holds an opaque key and SHA-256 digest. Authorized retrieval verifies the signature and package hashes and returns the stroke representation without a public or permanent object URL. Worklists expose no signature bytes. The current system retains signature artifacts with acknowledgement history and has no automatic deletion policy.
