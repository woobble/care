# Tenant isolation

The API treats the OIDC subject and requested tenant as untrusted until verified. A tenant header selects a candidate tenant; it does not grant access.

`OidcGuard` validates the access token and resolves its issuer plus subject to an active local user. `TenantContextGuard` opens the identity transaction, sets `app.user_id` locally, verifies an active membership and tenant, then sets `app.tenant_id` before loading role grants. Client, organization, and employee use cases check the requested permission and resource scope before accessing tenant data.

RLS is enabled and forced on tenant-owned tables. Identity membership policies allow self-membership reads when `app.user_id` is set. Role and grant policies also require the verified tenant context. Missing context returns no rows. The worker has a separate, explicit policy for outbox processing.

Access administration derives the tenant from the validated request context and rechecks the actor's current active membership before every mutation. Role assignments are restricted to roles in that tenant, and the actor must already be able to grant every permission in the requested role at each selected scope. Scope targets are validated against tenant-owned organizations and facilities; a database trigger checks polymorphic scope targets, while composite foreign keys bind role assignments to the same tenant as their membership. A verified email claim can accept only a matching pending invitation and creates a pending membership with no role grants.

Organization, facility, and team context is resolved inside the owning application services. Employees have an explicit owning organization; organization-scoped employee access follows that ownership, including employees who do not yet have a facility assignment. Facility-scoped access requires an active employee assignment to the scoped facility, while team-scoped access requires active membership in the scoped team. Employee list queries apply these rules before pagination. Employee details filter assignments and team memberships so a scoped reader does not learn out-of-scope relationships.

Composite foreign keys bind facilities and teams to an organization in the same tenant, employee assignments and team memberships to both the employee's owning organization and the selected facility or team, qualification and skill assignments to definitions in the same tenant, and employee user links to a same-tenant membership. The new tenant-owned tables have forced RLS policies. These checks complement API authorization; they do not replace resource-scope checks.

Professional competency policies, their immutable versions, and qualification requirements also use forced tenant RLS and tenant-qualified foreign keys. Policy administration requires the dedicated read or manage grant. Care-plan activation and evaluation check the action's care-plan permission and resource scope before evaluating the tenant's active operation policy. The evaluator locks the active version and the employee and qualification rows for the duration of the care-plan transaction, so policy rotation, employee deactivation, qualification archival, or assignment revocation cannot race past an authorization decision. Authorization evidence is written to audit and outbox in that same transaction and contains policy/version, employee, qualification IDs, and evaluation time, not care-plan narrative. See [professional competency authorization](../domains/professional-competency-authorization.md).

Workforce Compliance reads are tenant-bound and run under forced RLS for the tenant settings as well as the employee and competency data they project. The API checks `workforce_compliance.read` for summaries and worklists, `workforce_compliance.read_details` for employee-level findings, and `workforce_compliance.manage_settings` for threshold or reporting-timezone changes. Compliance permission does not widen employee visibility: the read path applies the shared employee visibility predicate before pagination, grouping, or summary counts. Organization scope follows employee ownership; facility scope requires an active employee assignment and active facility; team scope requires an active membership and active team. Multiple scopes are combined as a union, a matching tenant grant is tenant-wide, and no usable scope returns no employee rows. Application tenant predicates remain explicit in addition to RLS.

Settings updates append an audit record and versioned `workforce_compliance.settings_updated` outbox event with the tenant, settings version, and changed fields in the same transaction. A compliance read, an expiry date passing, or a derived finding does not write employee data or emit an event. See [Workforce qualification compliance](../domains/workforce-compliance.md).

Membership status is part of the authorization decision. Only active memberships can establish a tenant principal. Deactivation removes tenant access until an administrator reactivates the membership; revocation is terminal and invitations cannot restore a revoked membership. Audit and outbox records for access changes are written in the same database transaction as the access change.

Context uses PostgreSQL `set_config(..., true)`, so it is transaction-local and cannot leak to a later pooled connection. Application queries still include tenant predicates and authorization checks. RLS is defense in depth, not the fine-grained authorization model.

Integration tests connect as `care_app` and `care_worker`, not only as the migration owner. Changes to identity grants or RLS policies must retain tests for missing context, cross-user memberships, cross-tenant access, and transaction cleanup.

## Client and service scopes

New clients have tenant-safe composite references to one owning organization and one primary facility belonging to that organization. Organization-scoped client access follows the owning organization; facility-scoped access follows the primary facility. An unassigned legacy client is visible to a tenant-scoped user only and is omitted from organization and facility scope queries. Team and `assigned_clients` scopes do not grant client access because those relationships are not modeled yet.

Client addresses, contacts and contact roles, insurance records, and Pflegegrad history each have forced tenant RLS. Their APIs first authorize access to the parent client, then use tenant- and client-qualified child queries. Service categories, definitions, and availability have forced tenant RLS and composite references that keep categories and providers within the selected tenant. Service read scope additionally filters available services to the caller's organization or facility; catalog mutation permissions are separate from service read permission.

Service agreements and agreement-service rows also have forced tenant RLS, tenant-qualified foreign keys, and tenant-first indexes. Agreement reads and writes first authorize the associated client and then check agreement permission against its tenant, organization, and facility. Service selection runs through the catalog's tenant, archive, validity, and provider-availability checks. Client timeline projection includes agreement audit rows only when the row is a service agreement and its metadata names the already-authorized client; it returns fixed summaries rather than raw metadata.

Visits, planned visit services, assignments, employee unavailability, and generation history have forced tenant RLS and tenant-qualified provider, client, agreement, service, and employee references. Scheduling checks both `schedule.read` scope and compatible `client.read` scope before returning the limited calendar DTO. Tenant, organization, and facility schedule scopes are intersected with client scope. A team schedule scope includes only visits with an active assignment to an employee who is an active member of that team on the visit's local date; it does not expose unassigned visits. `assigned_clients` remains unsupported. Caregiver self-schedule and execution mutations resolve the local user to an active employee and require an active assignment on the requested visit; tenant or team scope alone is insufficient.

Visit executions and performed services have forced tenant RLS, tenant-qualified visit, service, agreement-service, and employee references, and application-level assignment checks. Execution reads also follow the visit/client resource scope. Office review uses `visit_execution.read`; administrative time corrections use the separate `visit_execution.correct` permission and record old/new values with a reason. Visit history and the client timeline return fixed summaries and actor IDs, never raw audit metadata or notes.

Care-documentation tables also have forced tenant RLS and tenant-qualified references to visits, executions, performed services, and employees. Caregiver detail reads and mutations require an active employee link and a visit assignment or recorded participation. Office detail and worklist reads use visit resource scope; the worklist filters scoped rows before returning personal details. Office amendments require `care_documentation.amend`. Detail responses contain narrative text, while worklist, audit, history metadata, outbox payloads, and client timeline summaries omit it.

Clinical-documentation tables also force tenant RLS. Each structured record references the tenant-qualified Care Documentation and execution. Its stored client reference is backfilled from the visit and a database trigger keeps it consistent with that parent chain, so composite foreign keys can bind later references to the same client. Draft writes lock and version the parent document. Caregiver mutation requires an active employee link and the same assignment-or-participation relationship as Care Documentation. Client history queries first resolve candidate visit records, then enforce clinical read/review permission against each visit's client, organization, facility, and team scope before returning values. Corrections append records linked to the original and cannot update finalized content.

Care planning requires a separate tenant-owned persistence and authorization boundary. Plan, revision, child, evaluation, and clinical-reference relationships must be tenant-qualified, with client, organization, and facility consistency checked against the provider context. Forced RLS is defense in depth; API reads and writes must still enforce the actor's client resource scope. The active-plan rule applies within a client's organization/facility provider context and must be protected against concurrent create or activation. Caregivers may read relevant active measures for an assigned visit; plan authoring and revision activation require their own management grant. A tenant match alone does not authorize access to care-plan narrative.

Evidence-package and acknowledgement tables use forced tenant RLS and tenant-qualified foreign keys to documentation, clients, representatives, employees, and packages. Package preparation and acknowledgement capture require the caregiver's employee-to-visit relationship; Office reads and revocation use the visit/client resource scope and separate permissions. Signature retrieval reauthorizes the package's visit and verifies both stored hashes before returning private stroke data. Worklists expose only scoped service-evidence metadata.

Medication definitions, orders, revisions, occurrences, administration records, and corrections also use forced tenant RLS and tenant-qualified foreign keys to clients, employees, visits, orders, and revisions. Every API query carries an application tenant predicate and performs client scope checks. Caregiver visit reads and writes additionally resolve the user's active employee link and require an active assignment to that visit and client; tenant permission alone does not provide caregiver access to medication histories. Administration and correction also require a passing competency policy evaluation in the same transaction. See [Medication management and administration](../domains/medication.md).
