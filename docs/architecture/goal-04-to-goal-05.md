## B. Architectural decisions

1. Tasks owns complete use cases and task-owned writes. Its only foreign-data dependency is OperationsTaskData; it never imports the facade or foreign persistence. The facade constructs the legacy adapter from UnitOfWork and passes the typed capability, never a facade instance or facade-bound callbacks. No competing public Tasks API or workflow framework was added.
2. Legacy foreign SQL stays at operations.application.ts, where its exact imported symbols are already baselined. The adapter validates sources/provider contexts, checks client access, resolves linked employees, supplies client visibility/name-search/local-date SQL, executes the existing display join with caller-supplied predicates/order/page bounds, and reads activity actor facts. It contains no lifecycle or worklist orchestration.
3. Task-only filters/counts/order/pagination/projections, operations scopes, summaries and all mutations moved. Foreign predicates remain correlated SQL rather than per-row API calls or materialized ID lists, preserving count/page semantics and query bounds.
4. createDeadlineTask stays in the facade: resolve/authorize current work item, then call delegated creation with the original sourceDeadlineKey. The task service retains advisory lock, duplicate lookup, unique-key semantics and write ordering. listWorkQueue still merges the same task and exception pages; dashboard still composes sources concurrently and receives task statistics from Tasks.
5. Task preflight source/client/scope reads keep their original separate transactions. Mutations retain their tenant transaction, positive expected-version validation and conditional update. No-op patches write nothing. Activity/audit/outbox stay atomic; comments append activity/audit without version/timestamp changes or an outbox event.
6. Task/client/source/assignment permissions and display redaction remain distinct. Existing scope SQL is split at its ownership boundary without changing predicates. No permission widening, new client requirement or new actor-name redaction was introduced.
7. A structural comparison matched **43 original method ASTs**, normalizing collaborator access, the equivalent summary query type and date-helper access. The three split methods (listTasks, taskActivityList, taskScopeConditions) were reviewed separately: existing joins, client predicates, actor lookup and SQL ordering/page bounds remain equivalent. PostgreSQL regressions exercise those splits.
8. Recurrence/deadline workers still insert ordinary tasks directly in their existing transactions. They own generation/idempotency/lease orchestration, not an alternative interactive lifecycle implementation. Existing shared assignee validation remains in operations-guards.ts. These worker paths were not redesigned.

Removal path for the adapter: introduce bounded, transaction-aware owner source/context/display/timezone capabilities with equivalent scope and completeness semantics, replace each adapter method incrementally, then remove resolved baseline symbols only after their remaining aggregation uses also disappear. Do not move the foreign imports to another local file or widen the baseline.

## E. Goal 05 preparation: Billing payments and receivables

Inspected modules/billing/src/application/billing.application.ts, domain/billing.ts and tests, claims/{claims.application,domain,schema,payer-schema}.ts, schema.ts, immutable/append-only migration protections, index.ts, API Billing/Claims composition, Billing/Document controllers, billing.integration.test.ts and consumers. Billing has no dedicated repository today; its application services issue Drizzle queries directly.

Recommended first extraction is seven public operations: **recordPayment, allocatePayment, reversePaymentAllocation, listPayments, listPaymentsPage, receivables, receivablesPage**. Keep invoice creation/issuance/corrections/PDF/export orchestration and claims lifecycle outside. exportReceivables remains a facade export bridge initially; its shared projection/facts must continue deriving identical balances.

1. **Recording/allocation:** recordPayment checks organization payment-manage permission, safe positive EUR cents ≤2,000,000,000, valid receivedAt/method and bounded reference fields; validates organization existence before appending payment/audit/outbox. allocatePayment locks payment, then invoice, then optional claim; checks issued invoice and same organization, payment-manage resource permission and optional claims.reconcile.
2. **Receivables:** receivablesPage computes issued total minus corrections minus unreversed allocations, applies provider/facility/client/recipient/due/search/status filters before count/page, orders by due date, descending issue date and invoice ID, and uses invoiceView. listPaymentsPage scopes at organization level, searches references/payer/invoice numbers, uses Europe/Berlin received dates, filters remaining amounts and orders by receivedAt/ID descending. Page size ≤100. Preserve array wrappers and pagination metadata.
3. **Financial consistency:** reuse assertPaymentAllocation, deriveReceivableStatus, assertCorrectionAmount and integer-cent arithmetic. Corrections cannot exceed outstanding receivables or per-line remaining amounts. InvoiceView and correctInvoice also use receivableFacts; the worker uses receivableFactsByInvoice. These must share one authoritative calculation, not independently diverging copies.
4. **Locks/transactions:** allocation takes SELECT FOR UPDATE on payment → invoice → optional claim, performs balance checks under those locks and atomically appends allocation/audit/outbox. Reversal reads allocation, locks payment → invoice → optional claim, checks prior reversal and appends reversal/audit/outbox. correctInvoice locks invoice before reading balance. Preserve this order to avoid allocation/correction races and lock inversions.
5. **Calculations:** facts are issued gross less correction sums and active payments; negative outstanding fails. Reversed allocations are excluded from balance totals but retained in histories. Receivable status precedence includes corrected, paid, overdue, partial, unpaid; existing SQL status filters and domain derivation must stay aligned. Catalog pricing/tax half-up rounding belongs to existing domain logic and is outside this extraction.
6. **Authorization:** payment listing/receivables use billing.payments.read; mutations use billing.payments.manage; invoice checks carry organization/facility/client resource facts. Optional claim links additionally require claims.reconcile. Existing SQL scopes/deny-by-default, forced tenant RLS, source-name behavior and permission differences must be characterized rather than inferred from documentation.
7. **Idempotency:** recordPayment has no general caller idempotency key; repeated valid recording creates another payment. Ordinary allocations may repeat if balances allow. Claim allocation rejects a second active use of the same payment for that claim; active total cannot exceed the latest accepted decision. Reversal uniqueness is (tenantId, allocationId), reinforced by locks and prior lookup. Preserve existing rejection/duplicate behavior; do not invent an API-wide idempotency scheme.
8. **Audit/outbox:** payment.recorded, payment.allocated, payment.allocation_reversed use the same transaction; claim-linked allocation additionally appends claim.payment_linked audit/event after the payment event. Reversal retains reason metadata/history and does not rewrite the allocation. Do not mutate immutable invoice totals or append-only payment facts.
9. **Claims dependencies:** claims and claimDecisions are Billing-owned tables despite separate files; importing them internally introduces no foreign-domain debt. The allocation path checks invoice association, claim status (accepted/partially_accepted/resubmitted), latest accepted amount and active allocations. ClaimsApplicationService.paymentSummaryInTransaction independently projects claim payment facts; preserve compatibility without redesigning claims. Payer schema and claim migrations remain untouched.
10. **Coverage/consumers:** billing.integration.test.ts covers payment search/remaining balances, partial/full payment, reversals, corrected receivables, claim acceptance/reconciliation denial, invoice/provider scopes, numbering, concurrent issuance and audit/events. Domain tests cover cent rounding, allocation/correction caps and statuses. Add focused allocation/reversal races, rollback, duplicate claim-payment links, reversal retry, received/due date boundaries and combined correction/payment scenarios where not protected. Operations consumes receivablesPage; its worker calls readOperationsReceivableDeadlines. BillingController, Documents export controller and pilot seed depend on the stable facade.

Important shared implementation: invoiceView (~220 lines) reads Clients names/addresses, Billing lines/corrections/payments/documents and performed services/evidence readiness. It only needs receivableFacts and the evidence capability from its enclosing service. It must become an independent transaction-aware projection collaborator if Payments needs it, not a callback to the Billing facade. Its foreign imports cannot simply move to a new file without new baseline debt. receivableFactsByInvoice is Billing-owned aggregate SQL already shared with the worker; it can move to an internal owner read helper with a compatible existing export bridge for readOperationsReceivableDeadlines.
