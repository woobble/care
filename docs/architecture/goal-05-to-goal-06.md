## B. Architectural decisions

1. Payments receives UoW, audit/outbox, Billing-owned settlement queries and a typed three-method invoice-data port. It owns actual orchestration and opens exactly the existing transactions. No facade instance or facade-bound method is injected, and there is no second public payments API.
2. Settlement queries centralize correction/active-allocation totals and outstanding amounts. Payment remaining arithmetic now lives with its allocated balance in paymentBalance, using the original single read. Batch facts retain their existing two aggregate queries. Correlated SQL expressions remain necessary for database count/filter/page behavior and now live with these facts, rather than in the facade or Payments.
3. Corrections, all invoice projections, payment allocation and readOperationsReceivableDeadlines use the same authoritative settlement helpers. deriveReceivableStatus, assertPaymentAllocation and assertCorrectionAmount remain the existing pure domain rules. Claim accepted-cap checks remain their original claim-specific orchestration; they do not replace invoice/payment balance checks.
4. InvoiceView moved into independent LegacyBillingInvoiceData at billing.application.ts. It depends only on settlement queries and the evidence readiness capability. Existing client names/addresses, performed-service/evidence checks, Billing correction/payment/document history and response shape are retained. Organization existence and client-name SQL are narrow port methods. This avoids moving baselined Client/Organizations/Visit Execution imports or adding per-invoice calls.
5. The legacy projector has no UoW: supplied transactions continue through its reads and evidence capability. The facade and Payments share one projector instance. Scope/audit helpers are pure functions with identical resource facts and metadata, rather than facade callbacks.
6. Allocation still locks payment → invoice → optional claim, then validates balances under locks and appends financial/audit/outbox facts. Reversal still reads the allocation then takes the same locks before prior-reversal detection and append-only reversal. Corrections retain the invoice lock. Existing operation ordering, Promise.all reads, rollback and error precedence are preserved.
7. Recording still has no idempotency key; repeated valid requests produce separate payments. Ordinary allocations may repeat within balances. Claim-linked active duplicate use and latest accepted-decision caps remain; a reversal is allowed once. Invoice/allocation originals are never rewritten.
8. The export-star public surface is protected: internal classes/functions are imported, not re-exported from billing.application.ts or index.ts. Only the four original data interfaces are re-exported. Runtime tests explicitly reject leaked internal classes; generated OpenAPI/client output has no diff.
9. Structural comparison matches 48 original method bodies after normalizing pure-helper and collaborator calls. The intentional foreign-query/balance splits were reviewed separately and exercised by PostgreSQL tests. This supports equivalence without substituting for financial/runtime checks.

Graphify regenerated the code graph successfully; changed communities received hub-derived fallback names. Semantic relabeling was not requested and is outside this AST-only refresh.

Legacy removal path: replace invoice display/address/name-search/provider/performed-service reads with narrow owner capabilities that accept the transaction and preserve scope, fallback, ordering and query bounds. Remove each baseline symbol only when no other facade workflow uses it. Moving foreign SQL to another local file or making broad per-invoice owner calls is not the removal strategy.

Do not standardize those differences by changing accepted inputs or default behavior.
5. **Transport versus business:** controllers mostly parse/map and call the public facade. VisitsController.changeStatus dispatches three operations and returns the same mutation projection; SchedulingOperationsController.report shares worklist/conflict mapping. Domain rules, scopes, locks, timezone correctness and route/publication behavior remain in the application/domain services. Extraction should thin transport ownership, not move domain decisions into controllers.
6. **Error/permissions:** OidcGuard and TenantContextGuard remain class guards; handlers pass the principal and some explicitly reject a missing principal with BadRequestException. Application checks remain authoritative. ProblemDetailsFilter maps Scheduling not-found to 404, validation to 400, lifecycle/version/provider/conflict errors to 409 and authorization separately; preserve both status/code and validation precedence.
7. **Mapping opportunities:** assignmentResponse in scheduling.controller.ts overlaps existing assignment mapping in scheduling.mapper.ts but has its current public shape. Audit context extraction and UUID/principal parsing can become Scheduling-specific transport helpers. Reuse existing requestContext and withoutUndefined; do not introduce a controller base class or validation framework.
8. **Tour boundary:** SchedulingToursController has seven routes matching the seven internal Tour use cases through SchedulingApplicationService. MyTodayTour/MyPublishedTours are separate caregiver routes. Tour responses currently rely on existing serialization; do not replace them with a new mapping contract. tourVersionSchema coerces numeric values whereas updateTourStopsSchema requires a number. Retain this difference.
9. **Composition/contracts:** SchedulingModule imports all twelve classes from scheduling.controller.ts and binds SCHEDULING_APPLICATION once. Generated SDK operation IDs derive from class/method names (for example SchedulingToursController and VisitsController); preserve names, routes, decorators, HTTP codes, tags, parameter metadata, DTO class/schema names and optional/nullability. Repeated ApiQuery decorators already exist on visit list metadata; removing them is not automatically contract-neutral.
10. **Consumers/tests:** Office planning uses visit/worklist/tour generated types and routes; caregiver screens use today/published tours/calendar. clients.integration.test.ts covers planning, availability, tours/publication/stale versions/authorization; calendar-subscriptions.integration.test.ts covers feed boundaries. Scheduling domain/application tests protect semantics, but focused transport parser/mapping and malformed-query cases are sparse. Add them before broader controller moves.
